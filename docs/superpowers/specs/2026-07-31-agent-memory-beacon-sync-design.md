# Agent Memory Beacon Active-Active Production Sync Design

## 1. Goal

Add a separately runnable `beacon-sync` subsystem to the existing Agent Memory
Beacon repository. A Windows machine may produce Codex or Claude Code
conversation content while offline or on another network, and a Mac authority
must eventually merge that content into the one canonical Obsidian Vault.

The system is active-active only at the production edge:

- Mac and Windows may both run agents and create conversation evidence.
- Mac remains the only canonical Vault writer and formal lifecycle authority.
- Windows receives a read-only, generation-verified replica.
- Syncthing carries immutable folders; Tailscale may provide the private network.
- No component relies on Syncthing conflict copies for semantic merging.

The 24-hour delivery target applies while both devices, the scheduler, and the
configured transport are online.

## 3. Authority And Trust Boundaries

### 3.1 Mac authority

Only the Mac may:

- write canonical session notes and formal memory;
- advance lifecycle revisions;
- rebuild recall indexes, graph data, compiled context, and reports;
- seal published Vault generations;
- issue processing receipts.

Remote events never contain an executable lifecycle command. An event that
claims to retract, supersede, expire, restore, or delete formal memory is
rejected. Existing lifecycle preview, expected revision, source digest, and
explicit approval requirements remain unchanged.

### 3.2 Windows producer

Windows reads local Codex and Claude Code JSONL transcripts and emits immutable
source events. It does not classify content into formal Decision, Error, Favor,
Workflow, Skill, or Learn records. Those decisions remain in the Mac harvester,
so both machines use one quality model.

### 3.3 Windows replica

The replica is a derived view. Managed files are made read-only. Local Obsidian
configuration and unmanaged files are outside the managed manifest. A local edit
to a managed file is drift: materialization stops and reports it instead of
overwriting the edit.

Skill and plugin source files may be replicated for inspection, but are marked
`skill-source`. Replica materialization never installs, imports, executes,
discovers, adds to `PATH`, or grants capabilities to them.

## 4. Transport Layout

Syncthing is configured with two physically separate one-way roots:

```text
Windows outbox (send-only) -> Mac inbox (receive-only)
Mac published (send-only)  -> Windows received-published (receive-only)
```

The canonical Vault is never a bidirectional Syncthing folder.

```text
outbox/
  v1/
    identity.json
    events/<producer-instance>/<seq20>-<event-id>/
      event.json
      objects/<sha256>
      ready.json

authority-state/                  # local Mac only
  ledger.sqlite3
  mirrors/<producer>/<stream>/<epoch>.jsonl
  quarantine/

published/
  v1/
    objects/<sha256-prefix>/<sha256>
    snapshots/<generation20>/snapshot.json
    snapshots/<generation20>/complete.json
    receipts/<producer>/<seq20>-<event-id>.json
    current.json

replica-state/                    # local Windows only
  active-generation.json
  verify-cache.json
  staging/
  rollback/
```

`event.json`, referenced objects, and `ready.json` are immutable after
`ready.json` is published. `current.json` is written only after every object,
snapshot manifest, and `complete.json` is durable.

## 5. Canonical Encoding And Identity

All protocol JSON is encoded with:

```python
json.dumps(
    value,
    ensure_ascii=True,
    sort_keys=True,
    separators=(",", ":"),
    allow_nan=False,
).encode("utf-8") + b"\n"
```

Protocol documents reject floats, unknown top-level fields, duplicate identity,
control characters, absolute paths, and path components equal to `.` or `..`.
SHA-256 values are lowercase 64-character hexadecimal strings.

Identity fields:

- `device_id`: stable human device identity; an authority inbox is bound to it.
- `producer_instance_id`: UUID generated by one installation. Reinstallation
  creates a new instance rather than resetting an old sequence.
- `seq`: strictly increasing global event sequence within a producer instance.
- `stream_id`: hash of agent and stable transcript session ID.
- `stream_epoch`: UUID changed when the source file is truncated or replaced.
- `logical_record_id`: `session:<agent>:<session-id>`.
- `event_id`: SHA-256-derived ID over producer, sequence, stream, cursor, kind,
  and payload hash.
- `source_cursor`: byte start and end in the original append-only JSONL source.

Wall-clock time is display and audit metadata only. It never selects a winner.

## 6. Event Protocol

Event schemas evolve by content kind rather than one global version:

- `transcript.chunk` schema v1: exact JSONL bytes ending on a complete record
  boundary.
- `transcript.gap` schema v1: a bounded oversized record that the existing
  parser would skip; it carries byte length and source SHA-256 but no original
  content.
- `attachment.blob` schema v2: a transcript-grounded reference to one bounded
  regular file under an explicit `attachment_roots` allowlist.

The ready document uses the same schema version as its event. Transcript v1
golden bytes and event IDs remain unchanged. Producers never create a new v1
attachment; the reducer may read an already-durable v1 attachment bundle only
through the explicit legacy validator so upgrades do not strand queued data.
Formal-memory record upserts and destructive lifecycle commands are not event
kinds in either schema.

An event contains:

```json
{
  "protocol": "agent-memory-beacon-sync-event",
  "schema_version": 1,
  "device_id": "windows-gpu-...",
  "producer_instance_id": "uuid",
  "seq": 1,
  "event_id": "event-...",
  "event_kind": "transcript.chunk",
  "created_at": "2026-07-31T12:00:00Z",
  "agent": "codex",
  "session_id": "session-uuid",
  "stream_id": "stream-...",
  "stream_epoch": "uuid",
  "logical_record_id": "session:codex:session-uuid",
  "source_cursor": {"start": 0, "end": 4096},
  "metadata": {
    "cwd": "bounded optional value",
    "timestamp": "bounded optional value",
    "is_subagent": false
  },
  "payload": {
    "sha256": "64-hex",
    "bytes": 4096,
    "media_type": "application/x-ndjson",
    "role": "transcript-source"
  },
  "extensions": {}
}
```

For an attachment, `extensions.attachment.reference_id` binds the producer
instance, stream ID and epoch, source record cursor, normalized source-locator
digest, original name, and payload SHA-256. The local path itself is never put
in the event. Surface MIME and filename metadata do not choose the canonical
Vault extension.

The producer writes the content-addressed object first, then `event.json`, and
publishes `ready.json` last. A crash-safe producer state stores an allocated
event before `ready.json`; retries reproduce or finish the same event and never
reuse its sequence for different bytes.

Default bounds:

- event JSON: 128 KiB;
- normal chunk: 16 MiB;
- oversized skipped record: 512 MiB of source address space;
- one event object: 32 MiB;
- one attachment: 32 MiB and no larger than either the event-object or replica
  object bound;
- one producer cycle: 32 events;
- inbox/outbox warning quota: 2 GiB.

An oversized JSONL record is represented by `transcript.gap`. The Mac mirror
creates an equivalent sparse skipped record ending in a newline, preserving the
incremental parser's semantics without transporting content the parser already
rejects.

## 7. Producer State Machine

Producer state schema v3 owns the global sequence, transcript cursors,
attachment queue, content-addressed attachment cache, and one crash-recoverable
pending event. v1 state migrates directly without rotating producer identity;
v2 transcript and attachment pending state is revalidated and rewritten with
v2 attachment reference IDs. Unknown versions, out-of-range cursors, or a
pending event that no longer matches its queued source fail closed.

```text
DRAFT -> ALLOCATED -> OBJECT_DURABLE -> EVENT_DURABLE -> READY -> ACKED -> GC
```

On the first normal collection run, existing transcripts are baselined without
historical upload. `collect --include-existing` is the explicit historical
bootstrap path. Transcripts first seen after baseline are emitted from byte zero.

The producer reads only JSONL files. ZCode is outside this feature's scope.
Source truncation creates a new `stream_epoch`; it never regresses an existing
epoch cursor.

Garbage collection requires a matching receipt with:

- producer instance, sequence, event ID, and event hash equal to the event;
- terminal `applied`, `noop`, or `rejected` status;
- `gc_allowed: true`;
- retention time already elapsed.

File age, Syncthing state, or object presence alone never authorizes GC.

## 8. Mac Ingress And Reducer

The Mac binds every configured inbox path to one expected `device_id`. Events
claiming another device are quarantined.

Ingress validates, in order:

1. root containment and no symlink/non-regular-file entries;
2. JSON size and exact schema;
3. ready/event identity and event SHA-256;
4. producer sequence and event uniqueness;
5. payload size and SHA-256;
6. allowed event kind and cursor invariants.

The SQLite ledger is schema v4 and has unique constraints on
`(producer_instance_id, seq)` and `event_id`. A higher sequence waits for the
missing sequence. The same identity with different bytes blocks the producer
stream and is never guessed through.

Ledger migration is a strict sequence of independent transactions:
`v1 -> v2 -> v3 -> v4`. Each transaction changes one schema step and commits
its metadata version before the next starts. A crash therefore leaves an exact
restart point instead of a half-upgraded table reported as current. v4 adds
`metadata_sha256` and `metadata_bytes` beside canonical and metadata paths plus
payload hash/bytes.

Validated chunks are appended to persistent transcript mirrors. Mirror filenames
include producer, stream, and epoch so their heartbeat cursors cannot collide,
while embedded metadata keeps the original canonical session ID.

Validated attachments produce two immutable canonical effects:

```text
Attachments/Agent-Memory-Beacon/remote/objects/<sha[:2]>/<sha>.<ext>
04-Feedback/remote-attachments/<device>/<producer>/<seq20>-<event-id>.md
```

The extension is derived only from payload signatures (`png`, `jpg`, `gif`,
`webp`, `pdf`, valid UTF-8 text, or `bin`). The metadata note records the stable
reference, source identity, original name, payload digest, and a link to the
blob without exposing the source path.

The authority acquires the existing
`04-Feedback/_logs/harvester.lock`, then:

1. stages all contiguous events;
2. durably extends each mirror, recovering or truncating partial appends;
3. calls the existing transcript harvester against each changed mirror;
4. rebuilds the canonical index once for the batch;
5. commits transcript heartbeat cursors;
6. marks events `applied_pending_publish` or `noop_pending_publish`.

Mac-local transcripts keep their existing direct harvester route in v1. The
remote reducer reuses the same harvester and lock; it does not introduce a
second memory classifier or rewrite the mature local path.

## 9. Snapshot, Receipt, And Recovery

After reducer success, the publisher builds a complete canonical generation.
File hashes are cached by trusted local stat identity, and objects are stored by
SHA-256. A generation includes:

- monotonic `generation`;
- content-derived `generation_id`;
- parent generation;
- complete managed file list with path, size, SHA-256, and content class;
- tombstones for files managed by the previous generation but absent now.

Default exclusions include:

- `.git`, `.obsidian/workspace*`;
- `04-Feedback/_logs`, `_rollback`, `_cleanup-backups`, `_raw-sessions`;
- temporary files, locks, caches, databases, credentials, and auth material.

Profile skill sources are included only as `skill-source`; secrets and
authorization material remain excluded.

No changed canonical content produces no new generation. A no-op event may
reference the current generation.

Only after `snapshot.json`, all objects, `complete.json`, and `current.json` are
durable does the authority bind event receipts. Reducer and publisher share an
`authority-cycle.lock`; before releasing it, the publisher atomically assigns
every currently unbound terminal ledger row to the sealed generation and
generation ID. Receipt files are written only from those frozen bindings.
For an attachment, binding additionally requires exact generation membership
for both canonical effects: the blob manifest row must match
`payload_sha256/payload_bytes`, and the metadata row must match
`metadata_sha256/metadata_bytes`. Missing or mismatched membership leaves the
row unbound, even if one file exists in the Vault. While the immutable inbox
event remains available, a later reducer cycle may reconstruct a missing effect
without rewinding sequence or invoking the harvester twice.
Receipt status is one of:

- `applied`;
- `noop`;
- `rejected`;
- `blocked`;
- `quarantined`.

Only the first three may set `gc_allowed: true`. Unknown major schemas,
identity/hash conflicts, and source sequence corruption remain blocked and do
not advance the producer sequence.

Crash recovery is forward-idempotent:

- an object without ready is ignored;
- ready without its object remains pending;
- a partial mirror append is verified, completed, or truncated to its recorded
  pre-append size;
- canonical writes without a ledger terminal state are re-harvested
  idempotently;
- pending publish events are bound before generation publication returns;
- a receipt-write crash retries the same frozen generation byte-for-byte;
- events reduced after sealing remain unbound for the next generation;
- receipt publication may be repeated byte-for-byte.

## 10. Replica Materialization

The Windows materializer ignores a new `current.json` until:

1. current, snapshot, and complete identities match;
2. every required object exists;
3. object size and SHA-256 pass;
4. every managed path passes the receiver allowlist and its `content_class`
   matches the path-derived class;
5. paths have no case-fold, Unicode-normalization, or file/directory-prefix
   conflicts and remain portable on Windows;
6. the parent generation matches the locally active generation, unless an
   explicit bootstrap is running.

Changed objects are verified into local staging before any managed replica file
is touched. Application uses a journal and rollback directory. Existing managed
files must match their previous manifest hash. Any third state is local drift
and stops the update.

Each destination write is atomic and made read-only before publication. On
Windows the temporary file stays pinned by one handle from write and fsync
through `FileRenameInfoEx`; delete and rollback paths are also handle-pinned and
reject reparse points. Windows 10 1809 / Windows Server 2019 build 17763 is the
minimum because safe replacement of an existing read-only target requires
`FILE_RENAME_IGNORE_READONLY_ATTRIBUTE`.

The apply journal is bounded to 4 MiB. The active-generation marker is the final
commit point. A failed apply restores the previous managed bytes; restart can
also complete an interrupted journal. File-to-directory and directory-to-file
transitions are supported, but an unmanaged local collision aborts and is
preserved. Initial materialization requires the explicit `--bootstrap` flag;
background `run` never supplies it.

## 11. Scheduling And Installation

The subsystem has one CLI:

```text
beacon_sync.py init
beacon_sync.py collect
beacon_sync.py reduce
beacon_sync.py publish
beacon_sync.py materialize
beacon_sync.py gc
beacon_sync.py run
beacon_sync.py doctor
```

`run` dispatches by configured role:

- `producer-replica`: collect, materialize, then GC acknowledged events;
- `authority`: reduce, publish, publish receipts.

`materialize --bootstrap` is the only command allowed to initialize an empty
replica from existing published history. It is intentionally excluded from
scheduled `run`.

`install_beacon_sync.py` installs only the synchronization subsystem:

- macOS component mode: one user LaunchAgent; the production path normally
  lets `install_runtime.py` include it in the existing stable-runtime
  transaction when authority sync is enabled;
- Windows: one current-user Task Scheduler task with `IgnoreNew`, logon and
  periodic triggers, UTF-8 environment, and a manifest-verified stable
  interpreter;
- optional Windows Codex and Claude Stop/SessionStart collector hooks.

It never runs as `SYSTEM`, never installs a network service, and never modifies
Syncthing or Tailscale credentials.

Windows does not bind a task or hook to a Git checkout. The installer builds or
reuses an immutable release at:

```text
%LOCALAPPDATA%\AgentMemoryBeacon\runtime\releases\<release-id>
```

The release manifest binds the allowlisted bytes, release ID, directory,
redacted runtime config, and `.venv\Scripts\python.exe`. Staging runs the
Windows synchronization module matrix, dependency installation, `pip check`,
producer `init`, quick Doctor, and full manifest verification before any task
or hook mutation. Task and selected hook changes are one ownership-checked
transaction; a foreign same-name task aborts. Existing releases are retained
in v0.7.0 and are not automatically cleaned.

## 12. Configuration

The existing `config.yaml` gains a disabled-by-default `beacon_sync` mapping.
The portable sync loader reads only this section and transcript discovery paths,
so the Windows producer does not import the POSIX-only canonical writer.

Authority inboxes use explicit bindings:

```yaml
beacon_sync:
  enabled: false
  role: "authority"
  state_dir: "~/.local/share/agent-memory-beacon/sync"
  outbox_dir: ""
  published_dir: ""
  replica_path: ""
  received_published_dir: ""
  inboxes:
    - device_id: "windows-gpu-example"
      path: ""
```

No directory is activated while its configured path is empty.
`attachment_roots` is a producer-side list of absolute source allowlists and is
included in the same non-overlap checks as state, transport, replica, inbox,
published, and canonical Vault roots. `max_attachment_bytes` must not exceed
either `max_object_bytes` or `max_replica_object_bytes`.

## 13. Verification Matrix

Automated tests must cover:

- producer baseline, append, retry, truncation, sequence persistence, and gap;
- ready written last and immutable event replay;
- duplicate, reorder, missing sequence, event/hash conflict, and unknown schema;
- partial object arrival and quota deferral;
- mirror partial append recovery and duplicate harvest retry;
- canonical lock sharing and lifecycle event rejection;
- snapshot generation, unchanged no-op, tombstones, and skill-source isolation;
- current-before-object, corrupt object, local replica drift, rollback, and retry;
- explicit bootstrap, bounded journals, file/directory shape transitions, and
  preservation of unmanaged collision files;
- receipt identity and GC authorization;
- receiver path policy, content-class matching, Windows reserved paths, case and
  Unicode collisions, separators, prefixes, long paths, and task XML;
- Windows handle-pinned temp replacement plus build-17763 minimum-version gates;
- concurrent process lock behavior;
- source Doctor CI, stable Doctor live, release manifest, and full unit suite.

Final verification includes a local two-device simulation with separate producer,
inbox, authority, published, received-published, and replica directories.

## 14. Deferred Work

Release v0.7.0 does not implement:

- a multi-writer canonical Vault;
- CRDT or line-based Markdown conflict merging;
- a custom network protocol, relay, account system, or cloud service;
- automatic skill installation or execution;
- automatic formal-memory destructive lifecycle actions;
- ZCode transport;
- receipt compaction or deletion;
- content signing and key rotation;
- high-availability Mac authority or leader election.
